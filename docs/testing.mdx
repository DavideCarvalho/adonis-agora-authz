## The memory store

For tests, point `default` at the `memory` store (or build one inline). It has
the same semantics as the Lucid store but keeps state in-process, so tests stay
fast and isolated.

```ts
import { AuthzService, MemoryPermissionStore } from '@adonis-agora/authz'

const store = new MemoryPermissionStore()
await store.givePermissionToRole('editor', 'posts.*')
await store.assignRole({ type: 'user', id: '1' }, 'editor')

const authz = new AuthzService({ store })
await authz.can({ id: '1' }, 'posts.edit') // true (wildcard)
```

## Testing a Bouncer ability

```ts
import { Bouncer } from '@adonisjs/bouncer'
import { AuthzService, MemoryPermissionStore, defineAuthzAbilities } from '@adonis-agora/authz'

const store = new MemoryPermissionStore()
await store.assignRole({ type: 'user', id: '1' }, 'admin')

const abilities = defineAuthzAbilities(new AuthzService({ store }))
const bouncer = new Bouncer({ id: '1' }, abilities)

await bouncer.allows('hasRole', 'admin')   // true
await bouncer.denies('can', 'posts.edit')  // true (no grant)
```

## Writing your own store

`PermissionStore` is the whole surface authz asks of a backend — Redis, Mongo, a
remote authorization service, an in-house table layout. Implement these twenty
methods and every feature in the package works against it unchanged:

```ts title="app/authz/redis_store.ts"
import type { PermissionStore, TenantScope, SubjectRef } from '@adonis-agora/authz'

export class RedisPermissionStore implements PermissionStore {
  // ...
}
```

**Schema**

| Method | Contract |
| ------ | -------- |
| `ensureSchema()` | Create or upgrade whatever backing structures you need. Called on first use; a no-op is fine for a store with nothing to create. |

**Roles & permissions**

| Method | Contract |
| ------ | -------- |
| `createRole(name)` | Idempotently create the role; return its id. |
| `createPermission(name)` | Idempotently create the permission; return its id. |
| `givePermissionToRole(role, permission)` | Attach a permission to a role, creating either by name as needed. |
| `revokePermissionFromRole(role, permission)` | Detach it. A no-op when either side is absent. |
| `getRolePermissions(role)` | The permission names attached to a role. |
| `listRoles()` | Every role name known to the store. |
| `listPermissions()` | Every permission name known to the store. |
| `deleteRole(role)` | Remove a role outright — revokes its grants, every user assignment, and the role row. Idempotent; an unknown name is a no-op. Whether to refuse a still-populated role is the host's call (`countSubjectsForRole` first). |

**Assignments & grants**

| Method | Contract |
| ------ | -------- |
| `assignRole(user, role, scope?)` | Assign a role to a user, optionally scoped to a tenant. |
| `removeRole(user, role, scope?)` | Remove the assignment matching that **exact** tenant scope. |
| `giveSubjectPermission(user, permission)` | Grant a permission straight to a user. |
| `revokeSubjectPermission(user, permission)` | Revoke that direct grant. Role-derived permissions survive. |

**Reads**

| Method | Contract |
| ------ | -------- |
| `getRolesForSubject(user, scope?)` | The user's role names, tenant-filtered. |
| `getSubjectsForRole(role, scope?)` | The reverse: every `{ type, id }` holding the role, tenant-filtered the same way. |
| `countSubjectsForRole(role, scope?)` | The same visibility as `getSubjectsForRole`, reduced to a count — the "N users" KPI without transferring one ref per member. |
| `countSubjectsByRole(scope?)` | Every role mapped to its member count in one pass (unheld roles count as `0`), for a whole roles matrix. |
| `getPermissionsForSubject(user, scope?)` | The user's effective permission names — role-derived ∪ direct. |
| `subjectHasPermission(user, permission, scope?)` | Exact-name membership check. |

**Transaction seam**

| Method | Contract |
| ------ | -------- |
| `withClient(client)` | A view of the store whose SQL runs on `client` (see [config → Joining a transaction](/docs/authz/config#joining-a-transaction)). A store with no connection to scope to — like the memory store — returns `this`. |

Four invariants hold across all of them, and a store that breaks any one of them
will pass casual testing and fail in production:

1. **Writes are idempotent and race-tolerant.** Assigning the same role twice
   concurrently must leave one assignment and throw nothing.
2. **Tenant visibility is asymmetric.** A global request (no tenant, or `''`)
   sees only global rows. A tenant request sees global rows **and** that tenant's.
   A tenant-scoped assignment must never surface in an unscoped check or in
   another tenant's.
3. **Direct user-permission grants are tenant-independent.** They apply in every
   scope. Only role assignments carry a tenant.
4. **Names match exactly.** `subjectHasPermission` and `getPermissionsForSubject` do no
   wildcard expansion — the store returns what was granted, `posts.*` included,
   and the service runs the [matcher](/docs/authz/concepts#wildcard-matching)
   over it. A store that expands wildcards itself will double-expand.

## The shared store contract suite

Do not verify those invariants by hand — run the same suite the built-in stores
pass. It is exported from the `@adonis-agora/authz/testing` subpath and runs
under Vitest:

```ts title="tests/unit/redis_store.spec.ts"
import { runPermissionStoreContract } from '@adonis-agora/authz/testing'
import { RedisPermissionStore } from '#authz/redis_store'

runPermissionStoreContract('RedisPermissionStore', () => new RedisPermissionStore())
```

The suite covers idempotency, role/permission grants and revokes, direct grants,
per-user isolation, tenant visibility, polymorphic user types, role deletion,
member counts (per role and per matrix, tenant-scoped), and a trailing
`{ client }` option accepted by every data method. The Lucid store runs it
three times — TEXT, INTEGER and BIGINT `subject_id` columns — so behavior provably
does not depend on the column type.

<Callout type="info">
  The contract factory must return a **fresh, isolated** store per call so cases
  do not bleed into one another.
</Callout>

## The same suite on real databases

`test/lucid_store_testcontainers.spec.ts` runs the **full contract suite** — plus
the transaction-seam scenarios — against ephemeral **Postgres 16** and **MySQL 8**
containers ([Testcontainers](https://testcontainers.com)), each on TEXT **and**
INTEGER `subject_id` columns. These are the things
only a real backend can prove:

- **the write path per dialect** — MySQL exercises `INSERT IGNORE`, SQLite and
  Postgres the `ON CONFLICT` form;
- **the DDL per dialect** — MySQL 8 has no `CREATE INDEX IF NOT EXISTS`, so the
  schema builder must make re-runs idempotent a different way;
- **the result shape per driver** — MySQL resolves raw `SELECT`s to the
  node-mysql `[rows, fields]` pair; Postgres yields `{ rows }`;
- **reads across connections** — a host transaction is invisible to the store's
  own connection until it commits. sqlite's single pooled connection physically
  cannot make this assertion, so every concurrency claim about
  `withClient` / `opts.client` / `resolveClient` rests on this file.

It needs a Docker daemon and **skips itself without one** — `pnpm test` stays
runnable everywhere, and CI (which has Docker) runs it. To run it alone:

```bash
pnpm --filter @adonis-agora/authz test:db
```

<Callout type="info">
  A downstream store for MySQL/Postgres should wire the same pattern into its
  own CI — `runPermissionStoreContract(name, freshStore)` needs only a
  `PermissionStore` factory; the containers are yours to launch.
</Callout>
